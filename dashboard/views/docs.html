Getting Started / Overview & Architecture

Engine Overview & Architecture

Build crash-proof, enterprise-grade Discord bot plugins on {{NAME}} with complete isolation, zero boilerplate, and native Discord Components V2 support.

How the Plugin Engine Works

The {{NAME}} Bot Host runs on a lightweight micro-kernel architecture. Instead of writing monolithic discord.js code, every feature is an isolated, hot-loadable Plugin. When a user runs a Slash Command, types a prefix command, clicks a button, or submits a modal, the engine handles all token auth, Discord Gateway WebSockets, cooldowns, permission caching, and invokes your plugin handler with a unified ctx (Context) object.

💡
Zero Gateway Headache

You never have to manually manage WebSocket shards, heartbeat ACKs, Discord rate-limits, or bot reconnection loops. The host engine manages Gateway lifecycle automatically and provides real-time latency via ctx.botPing and ctx.botUptime.

Core System Guarantees

  • Crash-Proof Error Isolation: If a plugin encounters an uncaught exception or async promise rejection, the host traps the error and sends a formatted error card to the user. The bot never crashes, and other active plugins remain unaffected.
  • Universal Dual-Engine Execution: Plugins write their logic once in onCommand(ctx). The engine automatically handles both Discord Slash Interactions and Gateway Text Message Prefixes (including custom server prefixes and bot mentions).
  • Universal Conflict Resolver: If a bot owner enables two plugins that share the same command (e.g., Prefix V1 and Prefix V2), the conflict engine automatically disables the older version and synchronizes the dashboard UI in real time.
  • Isolated Persistent Storage: Every plugin has access to its own disk-backed JSON key-value store (ctx.storage) that persists across bot restarts.

Quick Start in 3 Steps

  1. Create a self-contained plugin folder (e.g. my-plugin/).
  2. Create a readme.md containing metadata and optional configuration fields.
  3. Create a main/index.js exporting commands, handlers, and optional event listeners. Enable it via the dashboard with one click!

Commands & Routing / Subcommands & Groups

Subcommands & Subcommand Groups

Structure complex plugin commands into clean subcommand trees with automated route parsing.

Routing Architecture

Subcommands (Type 1) and Subcommand Groups (Type 2) allow you to bundle related actions under a single parent command. Inside onCommand, the engine exposes:

  • ctx.subcommand — Active subcommand name (e.g. "set", "view", "reset").
  • ctx.subcommandGroup — Active group name if nested inside a group (e.g. "channel").
  • ctx.options — Options specific to that subcommand.

Example 1: Two-Tier Subcommand Router (Prefix V2 Style)

main/index.js 
module.exports = {
  commands: [
    {
      name: "prefix",
      description: "Manage server prefix settings",
      slash: true,
      prefix: true,
      options: [
        {
          type: 1,
          name: "info",
          description: "View current server prefix"
        },
        {
          type: 1,
          name: "set",
          description: "Set a custom server prefix",
          options: [
            { type: 3, name: "new_prefix", description: "New prefix symbol (1-5 chars)", required: true }
          ]
        },
        {
          type: 1,
          name: "reset",
          description: "Reset prefix to default"
        }
      ]
    }
  ],

  onCommand: async function (ctx) {
    const sub = (ctx.subcommand || "info").toLowerCase();

    if (sub === "info") {
      const p = ctx.storage.get("prefix_" + ctx.guildId, "!");
      return ctx.reply({ content: "> Server Prefix is: `" + p + "`" });
    }

    if (sub === "set") {
      const val = (ctx.options.new_prefix || ctx.rawArgs[0] || "").trim();
      if (!val || val.length > 5) return ctx.replyWarn("Prefix must be 1 to 5 characters!");
      ctx.storage.set("prefix_" + ctx.guildId, val);
      return ctx.replySuccess("Successfully set server prefix to `" + val + "`");
    }

    if (sub === "reset") {
      ctx.storage.delete("prefix_" + ctx.guildId);
      return ctx.replySuccess("Successfully reset prefix to default `!`");
    }
  }
};

Prefix Engine, Mentions & Custom Aliases

How the engine evaluates incoming chat messages, resolves mentions, and handles customizable aliases.

Message Prefix Resolution Flow

When a Discord guild message arrives on MESSAGE_CREATE, the prefix dispatcher checks three tiers in order:

  1. Bot Mention Prefix: <@botId> command or <@!botId> command (always enabled).
  2. Server Custom Prefix: Guild-specific prefix stored in database (e.g. ?).
  3. Global Fallback Prefix: Bot's default prefix (configured in bot settings, default !).

Custom Aliases Support

Every command supports aliases defined in its manifest (aliases: [...]) as well as dashboard user-configured aliases stored in ctx.config.aliases. Both are automatically matched:

Dispatching Button Clicks

When a user clicks a button, the engine dispatches the interaction to enabled plugins using a 5-tier resolution hierarchy:

  1. mod.components[customId] — Exact match for fixed IDs (e.g. "confirm_delete").
  2. mod.onButton(ctx) — General button hook for component_type === 2 (best for prefix matching or dynamic IDs).
  3. mod.onSelect(ctx) — Invoked for dropdown select menus (component_type >= 3).
  4. mod.onComponent(ctx) — Generic component fallback for any interaction type.
  5. mod.components["*"](ctx) — Universal wildcard fallback.
⚠️
Avoiding "This component is not recognized."

If none of the enabled plugins register a matching handler for a button's custom_id, the engine sends an ephemeral warning: "This component is not recognized." Always ensure dynamic or session-based buttons (e.g. mute_confirm_xyz) are handled via onButton, components: { "*": fn }, or a Proxy object.

function getLatency(ctx) {
  try {
    const id = (ctx.data && ctx.data.id) || (ctx.interaction && ctx.interaction.id);

Glitch Prevention & Production Standards

Essential architectural guidelines to prevent command collisions, ghost pings, permission crashes, and Discord API rate-limits.

1. Dual-Engine Mention & Argument Resolution

In Discord Slash interactions, arguments arrive as structured objects (e.g. ctx.options.user). In Text Prefix mode, arguments arrive as space-separated tokens in ctx.rawArgs or ctx.rawText. Always use safe extraction helpers:

Safe Dual-Engine Argument Parser 
function resolveTargetUser(ctx, optName) {
  if (ctx.options && ctx.options[optName]) {
    const o = ctx.options[optName];
    if (typeof o === "object" && o.id) return o.id;
    if (typeof o === "string") return o.replace(/[^0-9]/g, "");
  }
  const arg = (ctx.rawArgs && ctx.rawArgs[0]) || "";
  const match = arg.match(/^<@!?(\d+)>$/);
  if (match) return match[1];
  if (/^\d{17,20}$/.test(arg)) return arg;

  return ctx.user ? ctx.user.id : null;
}

2. Safe Message Referencing & Ghost-Ping Immunity

When sending replies to chat messages, avoid pinging the author unless explicitly intended, and protect against Discord Error 10008 (Unknown Message) if the user rapidly deletes their trigger message:

Safe Reply Referencing 
function safeReply(ctx, payload) {
  let body = typeof payload === "string" ? { content: payload } : Object.assign({}, payload);
  if (ctx.data && ctx.data.id) {
    body.message_reference = { message_id: ctx.data.id, fail_if_not_exists: false };
    body.allowed_mentions = { replied_user: false };
  }
  return ctx.reply(body);
}

3. Auto-Delete Alerts vs Permanent Cards

Keep server channels clean and modern by following {{NAME}}'s message persistence standards:

  • Permanent Confirmations (ctx.replySuccess): Use for state changes that should remain visible in server history (e.g. prefix updated, coins transferred, ticket created).
  • Temporary Alerts (10s Auto-Delete): Use ctx.replyWarn, ctx.replyError, and ctx.replyCooldown. These messages automatically delete from Discord after 10 seconds, preventing channels from accumulating error spam.

4. Dynamic Cooldown Isolation

Always protect resource-intensive commands with ctx.cooldown(seconds). The engine automatically isolates cooldown timers per user, per command, and per plugin:

Command Rate Limiting 
onCommand: async function (ctx) {
  const isPrivileged = ctx.isServerOwner || ctx.hasPermission("ADMINISTRATOR");
  if (!isPrivileged && !ctx.cooldown(15)) {
    return; // ctx.cooldown automatically sends an animated cooldown alert with 10s auto-delete
  }

}

5. Two-Way Permission Verification

Never assume the bot has permission to perform an action simply because the user has permission to request it:

Defensive Permission Checks 
// 1. Verify User has rights
if (!ctx.hasPermission("MANAGE_MESSAGES")) {
  return ctx.replyWarn("You need Manage Messages permission to use this command!");
}

const res = await ctx.deleteMessage(ctx.channelId, targetMessageId).catch(function () { return null; });
if (!res) {
  return ctx.replyError("Failed to delete message. Please verify the Bot has **Manage Messages** permission!");
}

6. Asset & Nitro Fallback Handling

Standard Discord users may not have Nitro image banners. When building profile or user information commands, always support u.accent_color as a graceful fallback instead of failing with an error.

7. Preventing "This component is not recognized" Errors

When a button click or dropdown select interaction arrives, the engine queries loaded plugins in order. If your plugin sends interactive components, follow these best practices to ensure zero interaction drops:

  • Export both components and onButton: Registering your handler across both interfaces guarantees the engine catches the interaction regardless of dispatch strategy.
  • Prefix Dynamic custom_id strings: Always namespace custom IDs (e.g. plugin_action_id) and use a Proxy or wildcard (components: { "*": fn }) to capture dynamic session IDs cleanly.
  • Always Acknowledge Interactions: Discord interactions expire after 3 seconds. Always call ctx.update(...), ctx.deferUpdate(), or ctx.reply(...) immediately within your handler.

8. Zero Core Modification Rule (Complete Plugin Autonomy)

The host system is designed with a microkernel architecture. You never need to edit or touch any host system files to add features. Everything is driven entirely within your plugin:

  • Buttons & Click Handlers: Export in mod.buttons or mod.components. Supports wildcard prefixes ("action:*").
  • Dropdown Select Menus: Export in mod.selects or mod.components. Supports String, User, Role, and Channel select menus.
  • Form Modals (Pop-ups): Trigger with ctx.showModal(...) and handle via mod.modals[customId] or mod.onModal.
  • Custom Variables / Credentials: Define in mod.config (e.g. Lavalink Host, Port, Password) and read via ctx.config.
  • Embed Themes: Managed automatically by the engine via ctx.replyEmbed matching the bot owner's unified master color.
